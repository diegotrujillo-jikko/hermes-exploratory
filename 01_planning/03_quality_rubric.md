# Schema Quality Rubric

**Used to score Hermes-generated database schemas** during the exploratory phase.

This is your objective scoring system for comparing Spec A, B, C outputs across Sonnet, Opus, and Haiku models.

## Scoring Methodology

Total: **100 points**

Use this rubric for every SQL output generated by Hermes. Record the score in wan.db along with per-category breakdown.

---

## Category 1: Schema Structure (30 points)

**Criterion**: Does the schema have the correct tables, relationships, and fundamental design?

| Score | Criteria |
|-------|----------|
| **30** | All required tables present. All relationships correct (1-to-many, many-to-many, if applicable). Foreign keys properly defined. No extra/hallucinated tables. |
| **25** | All required tables present. 1–2 minor FK relationship issues (e.g., missing one FK, direction wrong). |
| **20** | All required tables present. 3–5 relationship issues. Still mostly correct structure. |
| **15** | Most tables present (1–2 missing). Significant relationship issues. Structure salvageable but needs rework. |
| **10** | Several tables missing. Major structural problems (e.g., completely wrong normalization, no FKs). |
| **0** | Schema is fundamentally broken or incomplete. |

**Scoring Tips:**
- Count the required tables you specified in the spec
- Check each table has the expected relationships
- Note any hallucinated columns/tables that don't match the spec

---

## Category 2: Naming Conventions (15 points)

**Criterion**: Does the schema follow specified naming patterns (snake_case, ID naming, timestamp naming, etc.)?

| Score | Criteria |
|-------|----------|
| **15** | Perfect compliance: snake_case throughout, `id` as PK, `{table}_id` for FKs, `created_at`/`updated_at`/`deleted_at` present, no abbreviations. |
| **12** | 1–2 deviations from naming conventions (e.g., camelCase in one column, missing one timestamp). |
| **9** | 3–5 deviations. Still mostly consistent. |
| **6** | Multiple deviations (6+ inconsistencies). Mixed naming styles. |
| **3** | Significant naming chaos. Inconsistent or non-standard throughout. |
| **0** | No attempt to follow naming conventions. |

**Scoring Tips:**
- Check every column name for snake_case
- Verify ID column naming (id, customer_id, product_id, etc.)
- Count timestamps (created_at, updated_at, deleted_at)
- Note abbreviations (cust_nm vs. customer_name)

---

## Category 3: Data Integrity & Constraints (20 points)

**Criterion**: Are appropriate constraints enforced (NOT NULL, UNIQUE, FK, PK, CHECK, soft deletes)?

| Score | Criteria |
|-------|----------|
| **20** | Excellent: All PKs and FKs defined. Correct NOT NULL constraints. UNIQUE where specified. Soft deletes implemented. No over-nullable columns. CASCADE/RESTRICT choices appropriate. |
| **16** | Good: All critical constraints present. 1–2 minor issues (e.g., missing one UNIQUE, one over-nullable). |
| **12** | Adequate: Most constraints present. 3–4 issues (e.g., some nullable FK, missing cascades). Still functional. |
| **8** | Weak: Several constraint issues (5+). Referential integrity partially enforced. Risk of data anomalies. |
| **4** | Poor: Major constraint gaps. Weak referential integrity. Data quality at risk. |
| **0** | No constraint enforcement. |

**Scoring Tips:**
- Check every FK has a matching constraint
- Verify NOT NULL on required fields
- Look for soft-delete timestamps (deleted_at)
- Check CASCADE/RESTRICT/SET NULL choices make sense
- Identify any obviously over-nullable columns

---

## Category 4: Comments & Documentation (15 points)

**Criterion**: Is the schema self-documenting with inline comments explaining design decisions?

| Score | Criteria |
|-------|----------|
| **15** | Comprehensive: All tables have descriptions. Complex columns have explanations. Design decisions documented (e.g., "soft delete for audit trail"). Foreign key choices explained. |
| **11** | Good: Most tables/columns have comments. Key decisions documented. Clear intent. |
| **8** | Adequate: Some comments present. Covers major entities but misses details. |
| **5** | Minimal: Few comments. Hard to understand design rationale without reading spec. |
| **0** | No comments at all. |

**Scoring Tips:**
- Read the comments as if you're a new team member
- Check if design rationale is clear (why soft delete? why this normalization?)
- Note missing explanations for non-obvious decisions

---

## Category 5: Query Feasibility & Performance (10 points)

**Criterion**: Can you actually query the schema to answer business questions? Are indexes suggested?

| Score | Criteria |
|-------|----------|
| **10** | Excellent: Schema supports all key queries (order history by customer, inventory by product, etc.). Appropriate indexes suggested or present. No N+1 query problems. |
| **8** | Good: Schema supports key queries. Minor performance concerns. Most indexes in place. |
| **6** | Adequate: Can answer most queries, but some inefficiencies (missing indexes, awkward joins). Workable. |
| **3** | Poor: Hard to write efficient queries. Missing indexes. Schema structure makes some queries difficult. |
| **0** | Cannot support key business queries without major rework. |

**Scoring Tips:**
- Think about queries from your spec (e.g., "Get all orders by customer", "Current inventory per product")
- Check if indexes exist on FK and composite queries
- Note any obvious N+1 problems or missing indexes

---

## Category 6: Adherence to Spec (10 points)

**Criterion**: Did the model follow your specification? Or did it hallucinate/deviate?

| Score | Criteria |
|-------|----------|
| **10** | Perfect: Model followed spec exactly. No unexpected deviations. All spec requirements met. |
| **8** | Good: Followed spec closely. 1 minor deviation that's still reasonable. |
| **6** | Adequate: Mostly followed spec. 2–3 deviations, but generally on track. |
| **3** | Poor: Deviated significantly. 4+ deviations. Hallucinated features not in spec. |
| **0** | Ignored spec entirely. |

**Scoring Tips:**
- Re-read your spec before scoring
- Check: Did the model add features not requested?
- Did it miss required entities or relationships?
- Did it use the right tech stack?

## Quick Scoring Tips

1. **Be consistent**: Use the same rubric for all 7 runs
2. **Compare side-by-side**: After scoring all outputs, create a comparison matrix
3. **Note patterns**: "Sonnet missed indexes but nailed naming"; "Opus over-engineered but thorough"
4. **Measure diminishing returns**: Score C - Score A = diminishing return value for Spec B
5. **Track what matters most**: If your domain cares about data integrity, weight that heavily in your analysis

## Adjusting the Rubric

If after a few runs you discover this rubric misses something important:

1. Document the gap
2. Add a new category or adjust weights
3. **Re-score all previous runs** with the updated rubric
4. Note the change in your analysis ("Updated rubric on 2026-05-17 to add Category X")

This keeps your metrics consistent and your comparisons valid.
