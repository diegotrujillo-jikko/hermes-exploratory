# Specification Variants

This directory contains the 3 CLAUDE.md-style specification documents you'll create during Week 1 of the exploratory phase.

## Files

- **`spec_a_minimal.md`** (~150 words)
  - Project overview, tech stack, basic architecture
  - Serves as baseline; expect hallucinations & gaps
  - Goal: Measure "what does Claude assume with minimal guidance?"

- **`spec_b_balanced.md`** (~480 words)
  - Spec A + coding conventions, data integrity rules, placement rules, safe change rules
  - Your team's standard specification depth for future projects
  - Goal: Find the "sweet spot" between detail and brevity

- **`spec_c_comprehensive.md`** (~900 words)
  - Spec B + examples, edge cases, testing expectations, detailed commands
  - Reference-quality; everything a junior dev would need
  - Goal: Measure diminishing returns (does C produce significantly better output than B?)

## How to Create Them

1. **Read** `planning/spec_a_b_c_template.md` for examples and structure
2. **Pick your problem domain** (order management, user auth, product catalog, etc.)
3. **Write Spec A first** (should take 30 minutes)
4. **Expand to Spec B** (add decision rules; ~1.5 hours)
5. **Expand to Spec C** (add examples and edge cases; ~2.5 hours)
6. **Get peer review** from Javier or Juan David before testing
7. **Commit to Git** with a meaningful message

## Template Structure (from planning/spec_a_b_c_template.md)

```markdown
# [Problem Name] Database

## Project Overview
- What is this system?
- Who uses it?
- Business constraints

## Tech Stack
- Specific technologies
- What NOT to use

## Architecture [optional in Spec A]
- Directory structure
- Data flow
- Where code goes

## Coding Conventions [Spec B+]
- Naming rules
- Data types
- Constraints

## Data Integrity Rules [Spec B+]
- Entity relationships
- Soft deletes
- Versioning

## File & Content Placement [Spec B+]
- When to create vs. modify
- Naming patterns

## Safe Change Rules [Spec B+]
- What NOT to change
- What to avoid

## Specific Commands [Spec B+]
- Real, working commands
- Deployment/testing steps

## Examples [Spec C+]
- Sample data
- Edge cases

## Testing & Quality [Spec C+]
- How to validate
- Acceptance criteria
```

## Naming Convention

Save as lowercase with underscores:
- `spec_a_minimal.md`
- `spec_b_balanced.md`
- `spec_c_comprehensive.md`

Or with your domain name:
- `spec_a_order_management_minimal.md`
- `spec_b_order_management_balanced.md`
- `spec_c_order_management_comprehensive.md`

## Review Checklist Before Committing

- [ ] All three specs follow the 150/480/900 word target (±20%)
- [ ] Each spec clearly builds on the previous (A ⊂ B ⊂ C)
- [ ] Naming conventions are consistent with your problem domain
- [ ] No personally identifiable information (clean for team sharing)
- [ ] At least one peer has reviewed and approved
- [ ] Saved as .md (markdown) files

## Tips for Good Specs

1. **Be specific, not vague**
   - Bad: "Use appropriate constraints"
   - Good: "All foreign keys must use RESTRICT to prevent orphans; soft deletes use deleted_at timestamps"

2. **Anticipate questions**
   - Spec should answer: Why this design? Why not that?
   - Include trade-off discussions in Spec C

3. **Keep it scannable**
   - Use headers, lists, tables
   - Avoid long paragraphs
   - Under 200 lines each (Nick's rule)

4. **Test against reality**
   - Can a junior dev build from this spec?
   - Is it too vague? Too detailed?
   - Does it match your actual needs?
